# Friction Log — 3D Capabilities (2026-03-08)

**Tester:** Claude Code (AI agent)
**Scope:** 3 journeys testing `cadtool run` with CadQuery scripts, error handling, and 2D/3D coexistence
**Overall verdict:** The 3D pipeline works. CadQuery scripts execute, STEP files export, versioning is correct. A few rough edges around failed runs and the relationship between 2D and 3D features.

---

## Journey 1: First Run

```
cadtool init --name "first-run"          → success
cadtool run box.py --output box_v1       → success, version 1
```

Script used:
```python
import cadquery as cq
result = cq.Workplane("XY").box(50, 30, 20)
show_object(result)
```

### What ended up on disk

```
./cadtool.json
./box.py                    ← original script (untouched)
./v1_box_v1/
  script.py                 ← copy of the script
  output.step               ← 15KB STEP file, valid Open CASCADE geometry
  meta.json                 ← version metadata
```

### Manifest after run

```json
{
  "name": "first-run",
  "objects": [],
  "versions": [{"version": 1, "label": "box_v1", "status": "success", "path": "v1_box_v1/"}],
  "current": "box_v1"
}
```

### meta.json

```json
{
  "version": 1,
  "label": "box_v1",
  "status": "success",
  "created": "2026-03-08T09:17:30.118184+00:00",
  "script": "v1_box_v1/script.py",
  "outputs": {"step": "v1_box_v1/output.step"}
}
```

**Result: Clean pass.** The STEP file is real — 15KB, starts with `ISO-10303-21`, generated by Open CASCADE 7.8. The script is copied into the version directory. Meta and manifest are both updated. `current` pointer tracks the latest version.

### Minor friction: version directory naming

The directory is `v1_box_v1` — the label is `box_v1`, and it gets prefixed with `v1_`. This means the user-chosen label appears twice: `v1_box_v1`. If I'd named my label `v1` the directory would be `v1_v1`. Feels redundant. The PRD examples show `v1/` (no label) and `v2_mounting_holes/` (label without version prefix in the label itself). Might be worth documenting the expected naming convention — should the user omit the version prefix from their label?

**Severity:** Low. Cosmetic. The agent doesn't care about directory names — it uses the paths from JSON output.

## Journey 2: Iterate

Three scripts run in sequence, plus two error cases:

```
cadtool run box.py --output solid_box         → v1, success
cadtool run shell.py --output shelled         → v2, success
cadtool run holes.py --output with_holes      → v3, success
cadtool run doesnt_exist.py --output bad      → error, script not found
cadtool run broken.py --output broken         → error, syntax error
```

### Versioning works correctly

- Auto-increments: v1 → v2 → v3
- `current` pointer advances with each successful run: `solid_box` → `shelled` → `with_holes`
- Each version gets its own directory with script copy, STEP file, and meta.json

### CadQuery execution is solid

All three scripts ran successfully — including non-trivial operations:
- `shell(2)` — hollowing a solid (v2)
- `pushPoints(...).hole(5)` — adding four holes to a face (v3)

These are real CAD operations that exercise the geometry kernel. Good validation that CQGI execution is working.

### Error: nonexistent script

```json
{"command": "run", "status": "error", "message": "Script file 'doesnt_exist.py' not found"}
```

**Clean.** No directory created, no manifest entry. Correct exit code 1.

### Error: invalid Python — FRICTION

```json
{"command": "run", "status": "error", "message": "Script execution failed: '(' was never closed (<cqscript>, line 2)"}
```

**Error message is good** — includes the actual syntax error and line number. Exit code 1. Correct.

**But a directory was created on disk:** `v4_broken/` exists with just `script.py` inside (no STEP, no meta.json). The manifest does NOT include v4_broken — only the three successful versions.

This is a problem:

1. **Orphaned directory.** There's a directory on disk that the manifest doesn't know about. If an agent lists files, it'll see `v4_broken/` but can't find it via `cadtool` commands. The PRD says "failed versions are kept" with a `_failed` suffix — but this directory has no meta.json and isn't in the manifest, so it's just debris.

2. **Version counter was consumed.** The next successful run would be v5 (not v4), since the failed attempt used v4. This is actually correct behavior — you don't want version numbers to be reused — but it means there's a gap in the version sequence with no manifest entry explaining why.

**Severity: Medium.** An agent seeing `v4_broken/` on disk with no manifest entry would be confused. Either:
- Record the failure in the manifest (with status "failed") and write a meta.json, per the PRD spec
- Or don't create the directory at all for failures (like the nonexistent-script case)

The current behavior is a hybrid that's worse than either clean option.

### Minor friction: no `--input` flag yet

The PRD describes `cadtool run script.py --input v1/output.step --output v2_holes` for iterative design where each script builds on the previous STEP file. This isn't implemented yet — each script starts from scratch. For Journey 2, I wrote each script as standalone (re-creating the box from scratch in each one). In a real workflow, you'd want to import the previous version's geometry.

**Severity:** Low for now — acknowledged as future scope. But it means "iterate on a design" currently means "rewrite the full script each time," which is verbose.

## Journey 3: Everything Together

Mixed 2D and 3D commands against the same project:

```
cadtool init --name "mixed-test"
cadtool add-rect ... --label "base plate"       → id 1
cadtool add-circle ... --label "center hole"     → id 2
cadtool add-circle ... --label "corner hole"     → id 3
cadtool run plate.py --output flat_plate         → version 1
cadtool run plate_holes.py --output plate_with_hole → version 2
cadtool delete --id 3                            → deletes corner hole
cadtool list                                     → count=2, 2D objects only
```

### Coexistence works

The manifest cleanly separates the two systems:

```json
{
  "objects": [
    {"id": 1, "type": "rect", ...},
    {"id": 2, "type": "circle", ...}
  ],
  "versions": [
    {"version": 1, "label": "flat_plate", ...},
    {"version": 2, "label": "plate_with_hole", ...}
  ],
  "next_id": 4,
  "current": "plate_with_hole"
}
```

2D shapes live in `objects`, 3D versions live in `versions`. They share the manifest file but don't interfere with each other. Delete on 2D objects doesn't touch 3D versions. This is clean.

### Bonus: `delete` now echoes the deleted object

```json
{"command": "delete", "status": "success", "id": 3, "deleted": {"id": 3, "type": "circle", "cx": 10.0, "cy": 10.0, "radius": 5.0, "label": "corner hole"}}
```

This was flagged as "very low severity nice-to-have" in the round 2 friction log. It's been implemented. Good.

### Friction: No connection between 2D and 3D

The 2D objects (rects, circles) and the 3D versions (CadQuery scripts) are completely independent. There's no way to say "run this CadQuery script using the 2D layout as input" or "these 2D shapes represent the top-down view of version 2." They're two parallel systems sharing a manifest.

This raises a question: what's the intended relationship? Some possibilities:
- 2D is a sketching/planning tool, 3D is the real output — they're intentionally separate
- 2D will eventually feed into 3D (e.g., a sketch that becomes an extrusion)
- They're separate features for separate use cases that happen to share a project

For an agent, the ambiguity is manageable — it just uses whichever system the task calls for. But it would help to have a documented stance on whether these are meant to converge.

**Severity:** Low. Not a bug — more of a product direction question.

### Friction: `list` only shows 2D objects

`cadtool list` returns the 2D objects but says nothing about 3D versions. An agent that wants a full project overview needs to read `cadtool.json` directly or there would need to be a separate "list versions" command. The PRD's `cadtool context` command would solve this — it's designed to return the full project state.

**Severity:** Low. Expected at this stage — `context` is planned for Milestone 7.

## Summary of Findings

### What's working well

1. **CadQuery execution via CQGI works** — real geometry operations (shell, hole) produce valid STEP files
2. **Versioning is correct** — auto-increment, unique directories, script copies, meta.json, current pointer
3. **2D and 3D coexist cleanly** — shared manifest, separate namespaces, no interference
4. **Error messages are good** — syntax errors include line numbers, missing files are caught early
5. **Previous friction log items were fixed** — delete echoes object, all improvements from round 2 held

### Issues to fix

| # | Issue | Severity | Notes |
|---|-------|----------|-------|
| 1 | Failed scripts create orphaned directories (no meta.json, not in manifest) | Medium | Either record failures in manifest per PRD spec, or don't create the directory at all |
| 2 | No way to list 3D versions via CLI | Low | `cadtool context` (M7) would solve this |
| 3 | Version directory naming is redundant (`v1_box_v1`) | Low-cosmetic | Document naming convention or strip version prefix from user labels |

### Viewer notes

- **macOS Preview cannot open STEP files.** The PRD lists GLB as the Preview-compatible format (Milestone 5), which is not yet implemented.
- **Autodesk online viewer** (drag and drop) works for STEP files and confirmed the geometry is correct.
- This reinforces the priority of GLB export — without it, there's no zero-friction way to visually inspect output on macOS.

### Questions for product direction

| # | Question |
|---|----------|

| 2 | Should failed runs be recorded in the manifest (as the PRD describes) or kept silent? |
